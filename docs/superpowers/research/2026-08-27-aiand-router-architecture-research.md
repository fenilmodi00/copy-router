# AI API Router Architecture Research (2026-08-27)

*How production AI API routers / gateways / proxies are built for mass use, what architecture they follow, and what that means for the `router` project (Go LLM proxy + the new aiand-key self-service login mode).*

---

## TL;DR — what we should adopt / avoid

1. **Adopt — split identity from inference config.** Every serious gateway keeps its control-plane / identity surface distinct from its inference surface (Portkey Control Plane vs AI Gateway, Cloudflare edge vs dashboard, vLLM `/v1` inference vs operational endpoints, network segmentation guidance). Our `AIAND_API_URL` shared between the OpenAI-compat inference base and the identity-probe root violates this — the blast radius of one mis-set env must not touch both surfaces.
2. **Adopt — wire the wipe as one tested operation.** Multi-tenant field practice centralizes tenant offboarding in a control-plane workflow (AWS SaaS Lens: onboarding/offboarding = a single repeatable mechanism, not one-off steps). We have the primitives (`SoftDeleteAccount`, `RevokeAllAccountSessionsForAccount`) but no orchestrator — `WipeAccount(ctx, id)` in one tx is the missing deep module (architecture-review candidate 5).
3. **Keep — opaque hashed server-side sessions, not JWT.** Repeatable consensus: interactive sessions belong in an HttpOnly/SameSite cookie bound to a server-side record; JWT best-practices explicitly warn against JWTs as persistent sessions; the strongest "refresh-token" design treats the token as opaque entropy and stores only its hash. Our SHA-256-hashed opaque cookie is the right shape. Hardening when scaling: HMAC-keyed (peppered) hash + family-based session rotation on reuse detection.
4. **Keep — tenant-scoped handlers behind one gateway surface.** LiteLLM and Portkey both scope per-request by tenant context on a single gateway surface. Our account-cookie → stashed `Installation` → unchanged admin handlers is that exact pattern. The flaw is not handler reuse; it is the 22-route registration duplication between selfhosted/selfserve (architecture-review candidate 1 — the Strong fix).
5. **Keep (with a documented invariant) — account id doubles as installation external_id.** Using an opaque registry key as the 1:1 tenant binding matches tenant-registry practice (AWS). The hazard is the overloaded role of the column: if it ever stops being exactly 1:1, the convention becomes a lie. Keep it, but record "account = installation external_id (1:1)" as an invariant, not a convenience.
6. **Adopt when scaling — provider circuit breakers + degraded-state broadcast.** Instawork/llm-proxy's config shape (failure threshold, window, cooldown, probe; `global_rate_limit_escalation_window` → synthesized degraded 503 so clients fall back instead of retry-storming) is the production-grade pattern. We have cluster scoring but no trip/cooldown today.

## Architecture patterns (deep dive)

### 1. Routing & dispatch layering

- **Who does this**: OpenRouter split routing into **model selection** and **provider selection** as two independent layers behind one OpenAI-compatible endpoint. Provider-layer failover is on by default; model fallbacks are opt-in via a `models` priority array (triggered on context-length errors, moderation flags, rate-limiting, downtime); you shape the candidate set with `order` / `ignore` / `only`, and `partition` controls whether fallback endpoints are grouped by model or ranked globally. Portkey adds canary/A-B routing, latency/cost-based selection, provider health checks, and weighted load balancing as "reliability automation"; the gateway exposes a single auth layer.
- **How** (per-layer): coarse-grained (model) routing first, then fine-grained (provider/variant) routing with live signals (health, latency, price, throughput percentile — OpenRouter even exposes `preferred_min_throughput.p90` / `preferred_max_latency` as routing constraints).
- **Our approach**: `internal/proxy` dispatch + `internal/router/cluster` scorers (AvengersPro, Multiversion) + catalog-driven model→provider binding + fallback via cluster. We already do layered selection; what we lack is the client-visible knobs (per-request provider pinning / fallback ordering across multiple providers) — today aiand is effectively the single routable upstream in the deploy baseline.
- **Verdict**: Design aligned with the field. When a second provider family lands, adopt the OpenRouter `order`/`ignore`/`only` shape rather than inventing a new knob.

### 2. Provider-adapter + wire-format translation

- **Who does this**: Helicone's Rust gateway is structured with provider-specific mappers + balancers on the request path and `endpoints/mappings.rs` transforming between provider formats; its Anthropic adapter is a 1,921-line file isolating ALL Anthropic wire/auth complexity (three credential sources + OAuth token refresh + identity spoofing + adaptive-thinking budget negotiation + beta headers). LiteLLM's adapter pattern is a `CustomLogger` subclass with 3 translation methods (`translate_completion_input_params` etc.) registered per `pass_through_endpoint` — "input translation" to OpenAI format, then reverse on output. LLM-Rosetta (arXiv 2604.09360) proposes a **hub-and-spoke intermediate representation** with a `ConversionContext`: provider-specific fields with no target-format equivalent (Anthropic `cache_control`, Google `grounding_metadata`) are silently dropped **with a warning recorded**; semantically-shared fields are preserved.
- **How**: either per-pair direct conversion (new provider = new matrix entries) or spoke-through-an-IR (new provider = one adapter). The IR wins as providers proliferate; direct-pair wins when the set is small and stable. Both enforce the locality rule "every provider's wire complexity lives in exactly one file."
- **Our approach**: `internal/translate` (OpenAI ↔ Anthropic ↔ Gemini, pure, no I/O — a direct-pair set), `internal/providers/openaicompat` for aiand, `internal/providers/aiand` for the identity probe. We already isolate per-provider logic in the right layer.
- **Verdict**: Matches field practice. If a 4th wire format appears, evaluate the IR shape (`translate` already reads like a small IR with the openai→anthropic→gemini matrix) before adding pair-conversions. Worth adopting from LLM-Rosetta: record-field-drop with a warning in a conversion context — today a field with no target equivalent is dropped silently with no log surface.

### 3. Caching (semantic / response cache)

- **Who does this**: Portkey offers **Simple** (exact-match, works across all models incl. image-gen) and **Semantic** (cosine-similarity match, ideal for near-duplicate prompts) cache modes. Cloudflare's exact-match response cache (TTL ≤ 1 month) cuts latency up to ~90% and caches first-byte for streams. Kong's **AI Semantic Cache** runs on Redis / pgvector / Valkey (enterprise). LiteLLM marks cache per-key/team and distinguishes its own semantic cache from provider-native prompt caching.
- **Our approach**: `internal/router/cache` (semantic response cache) + pubsub cross-instance invalidation + prompt-cache accounting in proxy. The semantic-cache shape matches Portkey; the pubsub invalidation edge is something several production apps get wrong (a well-known LiteLLM production cache-invalidation bug class surfaced during research).
- **Verdict**: Correct direction and ahead of typical self-hosted setups on invalidation. Key field lesson: cache config is per-tenant (per-virtual-key / per-account) — our stashed-Installation scoping supports that; make sure the semantic cache keys/namespaces by installation, not globally.

### 4. Rate limiting & quota

- **Who does this**: Helicone: header-driven policy `[quota];w=[time_window];u=[unit];s=[segment]` (`Helicone-RateLimit-Policy: 1000;w=3600` = 1000 req/hour) applied at the gateway edge. Cloudflare: free rate limiting on every plan + spend limits by model/provider (daily/weekly/monthly dollar caps, not just request caps). Instawork/llm-proxy: `global_rate_limit_escalation_window` — sustained global 429s (>~60s) flip the proxy into **degraded mode**, returning a synthesized 503 so clients fall back elsewhere instead of retry-storming; per-provider circuit breaker (threshold/window/cooldown/probe) with a `retry_contribution_mode` knob.
- **Our approach**: per-IP login-failure LRU caps (5 per 5 min) + admin limiter on the auth path. No global-degraded escalation on the inference path yet.
- **Verdict**: Our per-IP limiter for *authentication* is the right place (auth endpoints must always be rate-limited — OWASP). The escalation-to-degraded + per-provider circuit-breaker pattern is the missing piece for *inference* under mass use; adopt the Instawork shape when multi-provider fallback exists.

### 5. Key management & BYOK

- **Who does this**: LiteLLM: **virtual keys** are the tenant-scoped credential; the master key is env-set (must start `sk-`, rotated via a documented flow) and provider credentials are encrypted at rest with `LITELLM_SALT_KEY` (set once, never change — the same shape as our Tink AES-256-GCM encryptor). **JWT→Virtual Key Mapping** lets an OIDC claim (e.g. `email`) resolve to an existing virtual key WITHOUT distributing an API key at all — per-client budgets/RPM/TPM/model access/spend tracking all apply; rotation is admin-only; unmapped claims fall back to team-level controls. Cloudflare BYOK stores keys in a Secrets Store → easier rotation + per-key rate limits/budgets. Vercel BYOK: a failing BYOK request **falls back to platform system credentials**, billed against the credits balance; BYOK spend is metered separately and deliberately **not** counted in budgets (a budget can't cap a user's own-key spend).
- **Our approach**: `auth.APIKey` hashing + `Encryptor` (Tink AES-256-GCM), BYOK secrets at rest via encryptor, `byok_enabled` opt-in per installation, BYOK turns debit no inference cost, optional `BYOK_FEE_RATE` as a separate `byok_fee` ledger row. This is the LiteLLM/Cloudflare/Vercel shape with a cleaner fee-splitting distinction (`byok_fee` ledger row ≈ Vercel's `upstreamInferenceCost` vs `totalCost` telemetry split, plus `isByok` flag).
- **Verdict**: Aligned, ahead on the fee-split. Two adoptions when scaling: (1) the Vercel fallback-to-platform-credits semantic — only when a deployment *wants* to spend platform budget on BYOK failure; our managed-mode 400-on-missing-auth is the conservative inverse and should stay the default; (2) LiteLLM-style JWT/SSO→key mapping as the natural next auth surface for org onboarding (it removes API-key distribution entirely).

### 6. Billing / usage metering

- **Who does this**: All major 2026 gateways pass provider token rates through without a per-token markup and monetize via a platform/credit fee (OpenRouter 5.5%, Cloudflare 5% Unified Billing, Vercel pay-as-you-go credits, Portkey subscription) — BYOK further drops the fee (LLM Gateway 0% with own keys; OpenRouter free to 1M req/mo). LiteLLM tracks spend per virtual key/user/team with budgets and spend alerts; Vercel exposes `totalCost`, `upstreamInferenceCost`, `usage` per generation.
- **Our approach**: catalog price book + `internal/billing` balance checks + inference debits + `byok_fee` ledger rows.
- **Verdict**: Our structure matches the ledger model. The field pattern to adopt when pricing becomes dynamic is per-tenant budgets with spend alerts (daily/refresh-period caps) — Cloudflare's dollar-cap-not-request-cap framing is the one to copy.

### 7. Session / sticky-routing

- **Who does this**: OpenRouter uses `provider.order` with `allow_fallbacks:false` for compliance/BYOK/region pinning — "sticky" in the sense of try-this-first and stop. No session-based stickiness is a headline feature in the surveyed gateways; routing is stateless, selection is per-request based on live signals.
- **Our approach**: `internal/router/sessionpin` (Pin types + Store iface) + client_session_id derivation in proxy — we have real sticky routing.
- **Verdict**: We're ahead here; the field's answer to "must-hit-one-provider" is the OpenRouter pin/order knob, which is the routing-config analog of our session pin. Keep ours; consider exposing the pin semantics through a request header for eval parity with OpenRouter-style pinning tests.

### 8. Observability (tracing / metrics)

- **Who does this**: Gateways universally treat per-request observability as core: Vercel exposes per-generation telemetry (`latency` = time-to-first-token, `generationTime`, token counts, `isByok`, `providerName`, `finishReason`); Helicone's AI Gateway logs sessions, users, custom properties, cost tracking, with Proxy and Async modes (async logging keeps telemetry off the critical path); OpenTelemetry integration is standard (Cloudflare OTEL; Kong publishes OTel span attributes); per-decision span emitters + cost attribution are table stakes in the "2026 reference".
- **Our approach**: `internal/observability/otel` per-decision span emitter + `apm` (gin HTTP spans + Go runtime metrics) + slog with correlation fields + `internal/timing`. The 2-layer OTel split (per-decision vs HTTP/runtime) is unusual and deliberate.
- **Verdict**: Already strong. The Helicone distinction worth borrowing: **keep logging off the critical path** (our SafeGo fire-and-forget already does this for telemetry) and keep cost attribution on every decision row — we do.

### 9. Multi-tenancy & per-tenant isolation

- **Who does this**: AWS SaaS Lens: **pooled vs silo** isolation models, a **tenant registry**, and enforcement that "holds even when application logic is wrong" (leading-keys on DynamoDB, scoped credentials via STS/token-vending machine rather than trusting app code). The field's sharpest guidance: isolation spans **data, identity, performance, and analytics layers** — "analytics/reporting surfaces are the most common and overlooked isolation failure point." LiteLLM's tenancy hierarchy (org→team→user→key) is the canonical RBAC shape; spend/limits/model access inherit down the hierarchy.
- **Our approach**: one installation per aiand user (`model_router_installations`), account id = installation external_id (1:1), account-scoped `/admin/v1` handlers reading the stashed Installation, metrics scoping per installation.
- **Verdict**: Our pooled model with per-request installation scoping matches the AWS pooled pattern. The field lesson to internalize: the ANALYTICS surface must scope by installation just like the data surface — our `internal/api/analytics` is ra_-key only (read-only routing-decision export), but when selfserve accounts get "my usage" views, they must read through the same stashed-Installation scoping, not a separate analytics path.

### 10. Self-service onboarding / login

- **Who does this**: LiteLLM: **Internal User Self-Serve** — users onboard and manage their own keys (Admin UI + `/user/new` `/team/new` `/key/generate` REST webhook-style surface); SAML 2.0 SSO added for the admin UI alongside Google/Microsoft OAuth; JWT→key mapping for SSO'd users. TrueFoundry/AWS: SSO (OIDC/SAML) login buttons on the gateway login page, IdP-driven (Okta, Google, Azure AD, Keycloak) — orgs centralize identity, the gateway hooks into it. AWS SaaS Lens: onboarding must be **centralized in the control plane and fully automated** — self-service signup and admin portal funnel into the same workflow.
- **Our approach**: aiand-key self-service login — user presents an `sk-` key, we probe `GET /api/v1/me`, upsert account + installation, mint an opaque hashed cookie session. No SSO, no password.
- **Verdict**: Our flow is a valid self-service pattern (provider-credential-as-identity), similar in spirit to LiteLLM's self-serve but with provider auth instead of a username/password. The field's gap in our design: **no org-self-service surface yet** — LiteLLM's `/user/new`-style admin surface for *managing* keys/teams post-login is the natural next milestone (we already have the `/admin/v1` handlers; they'd need only a `scope`-checked wrapper). SSO (OIDC/SAML) is the eventual enterprise path for org-admins, and the JWT→key mapping pattern is the bridge that keeps our virtual-key model intact.

### 11. Scale & reliability (pooling, retries, circuit breakers, hot-reload, cache invalidation)

- **Who does this**: Instawork/llm-proxy (Go): config-driven circuit breaker (failure threshold in a sliding window, cooldown, probe), retry classes (transient vs rate-limit), global 429 escalation→degraded 503, test/fuzz modes. CC-Relay (Go, close cousin of our shape): connection pooling + HTTP/2 multiplexing, SSE immediate flush, goroutine-per-request with ctx timeouts/cancellation, thread-safe Ristretto cache, bounded signature cache with LRU, key pooling for rate-limit distribution, URL parsing once at init, automatic SSE header injection. Portkey: heartbeat delta sync (1-min) with local cache → hot-reload of config WITHOUT a deploy; gateway survives Control-Plane loss. LiteLLM prod guide: separate migrations job from proxy instances, master-key rotation flow, Redis for cross-instance cache invalidation and rates — cache-invalidation bugs across instances are a known real failure class. Cloudflare: automatic retries up to 5 with backoff. Glukhov (circuit breaker in Go): "a circuit breaker without timeouts is weak; retries without jitter create storms; fallback without metrics hides an outage."
- **Our approach**: `internal/providers/httputil` shared transport, `internal/timing` per-request stamps, pubsub cross-instance cache invalidation + recharge notify, OTel tracing, direct-SSE. We do NOT yet have per-provider circuit breakers or a degraded-state broadcast for the inference path.
- **Verdict**: Strong fundamentals (shared transport, pubsub invalidation, SSE). Adopt next: per-provider circuit breaker + degraded-503 broadcast (Instawork shape) once multi-provider fallback lands; hot-config reload via the DB→cache delta pattern (Portkey's heartbeat) is worth evaluating for routing-preferences — today a config change is a boot-time read, not a live delta.

## Contrast with our design (the 5 specific choices)

### (a) account id doubles as installation external_id (1:1, no FK)
- **Field**: Tenant registries bind a tenant to its resources via a single registry key; AWS explicitly warns that isolation must hold at the *enforcement* layer, and that a registry key must map to exactly one tenant boundary. Silo model would give each tenant a dedicated schema/table (overkill for us); pooled model uses a per-row tenant key — which is exactly our external_id-with-account-id.
- **Verdict**: **Keep** — this is textbook pooled multi-tenancy. The risk is the overloaded *role* of the column: when account id is *also* the installation external_id, any future "one account, many installations" (or vice versa) breaks the invariant silently. Record it as an explicit invariant in `CONTEXT.md` + a compiled assertion (one active account per installation) rather than relying on the convention.

### (b) wipe-on-key-revocation contract
- **Field**: Onboarding/offboarding centralized in the control plane, fully automated, single mechanism (AWS SaaS Lens); revocation of a credential → immediate, server-enforced invalidation, not client-side or expiry-only (session-management guidance: server-side deletion/flagging is the only reliable offboarding).
- **Verdict**: **Keep, but wire the orchestrator.** Our contract is sound and more aggressive than most (which just revoke access). The gap is operational: `SoftDeleteAccount` + `RevokeAllAccountSessionsForAccount` + installation removal exist as three primitives with NO caller. A `WipeAccount(ctx, id)` domain method (one tx, all three) turns the documented contract into executable truth and gives the future key-revocation webhook/cron a single seam. This is architecture-review candidate 5.

### (c) SHA-256-hashed opaque cookie sessions (not JWT)
- **Field**: The surveyed guidance converges hard: interactive sessions = HttpOnly+SameSite cookie bound to a server-side record you can revoke; JWTs are for stateless machine-to-machine flows and JWT best-practices explicitly warn against persistent-JWT sessions (no server-side logout); even refresh tokens are best treated as opaque entropy with only a hash stored (the redis-family-rotation example stores `HMAC-SHA256` digests and revokes whole families on reuse). Revolution via DB row update = the "delete the record" pattern.
- **Verdict**: **Keep** — we're on the field-approved side. The session-table semantics (revoke one / revoke all, `last_seen_at` touch, hashed token under an 8+4 prefix) exactly mirror the recommended server-side model. Hardening options when scaling: keyed HMAC hash (pepper) rather than bare SHA-256, and rotation-family reuse detection on the refresh path.

### (d) account-cookie-scoped /admin/v1 reusing the same dashboard handlers
- **Field**: LiteLLM and Portkey both reuse ONE handler surface scoped per-request by tenant context (the gateway is "the same admin surface" for every tenant; what differs is the tenant context, not the handlers). This is the pooled-model norm.
- **Verdict**: **Keep the concept** — this is correct and matches the field. **Fix the mechanism**: the 22-route duplication between selfhosted/selfserve is the real defect (architecture-review candidate 1 — Strong). The scope difference (dashboard vs full-mgmt) and the auth middleware (cookie vs admin-password) are exactly the parameters a shared `registerAccountScopedRoutes(group, scope, ...)` helper should take, so a new endpoint lands in one call site, not two.

### (e) AIAND_API_URL shared between the OpenAI-compat inference base and the identity-probe root
- **Field**: Identity/control surfaces are separated from inference surfaces everywhere serious: Portkey ships a separate Control Plane whose auth surface synced on a heartbeat; Cloudflare exposes its dashboard/management separately from the gateway edge; vLLM's security doc explicitly warns that "many other sensitive endpoints are exposed on the same HTTP server" and pairs endpoint protection with network segmentation to limit blast radius; least-privilege guidance says one mis-set config should not broaden the damage of a compromised credential.
- **Verdict**: **Adopt the split.** One env var feeding both the OpenAI-compat inference base (default `.../v1`) and the identity-probe root (default `https://api.aiand.com`) means an operator override that satisfies one consumer silently breaks the other, and a compromised deployment key can reach the identity surface with the same base. The low-effort fix (architecture-review candidate 3): resolve both endpoints in one place (`aiand.Endpoints{InferenceBase, IdentityBase}`), with a second explicit env for the inference path when bespoke. This is the single most-operationally-tangible adoption from this research.

## Recommendations for our project (prioritized)

1. **Split the aiand endpoint config** — `aiand.Endpoints` value object resolving `AIAND_API_URL` (identity root) and `AIAND_INFERENCE_PATH`/inference base separately; wire both consumers in `main.go` from the one struct. **Effort: S.** Direct blast-radius reduction; unblocks the ops story for operator overrides. (Candidate 3.)
2. **Extract `registerAccountScopedRoutes`** in `internal/server` — one call site for the 22-route dashboard surface, parameterized by scope + auth middleware + `deployedModels`/`aiandCatalogHandler` guards. **Effort: S–M.** Kills the silent-omission bug class when a new dashboard endpoint lands. (Candidate 1 — Strong.)
3. **Add `Account.WipeAccount(ctx, id)`** as a single-tx domain operation (accounts.SoftDelete + sessions.RevokeAll + installation removal) with a unit test against the in-memory fakes; the future key-revocation webhook becomes a thin caller. **Effort: M.** Turns the documented wipe contract into executable truth + atomic boundary. (Candidate 5.)
4. **Record the external_id invariant** — "account id = installation external_id, 1:1, one active account per installation" in `CONTEXT.md` with a compiled check; keeps design choice (a) honest as accounts scale. **Effort: S.**
5. **Add per-provider circuit breakers + degraded-503 broadcast** (Instawork shape: threshold/window/cooldown/probe + global-429 escalation) when the second provider family lands. **Effort: M–L.** Prevents retry-storms on dead upstreams under mass use; pairs with our `ErrClusterUnavailable`→503 mapping.
6. **Semantic-cache per-installation namespacing audit** + adoption of "record dropped translation fields with a warning" (LLM-Rosetta `ConversionContext`). **Effort: S.** Isolation + surfacing silent field loss.
7. **Evaluate Portkey-style heartbeat delta sync for hot-config reload** of routing-preferences/excluded-models — a config change should reach running instances without a boot. **Effort: L (architecture).** Today our pubsub handles cache invalidation but not live config; worth a design spike when a second replica enters the picture.
